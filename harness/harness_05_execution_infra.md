# 실행 인프라 계층 (Layer 2 — 규칙을 시스템으로 강제하기)

> 거버넌스 문서(00~04)가 "규칙을 적은 것"이라면, 이 문서는 그 규칙이
> 사람 기억에 의존하지 않고 구조적으로 지켜지게 만드는 실제 설정들입니다.

---

## 1. 버전관리 / 브랜치 전략

**원칙:** 실행 단위(TRD 1개) = 브랜치 1개. AC 통과 전에는 메인 브랜치에 못 들어온다.

```
main                        ← 항상 배포 가능한 상태만 유지
 └─ feature/{unit-code}      예: feature/a3-core-feature
```

- 브랜치명 규칙: `feature/{작업지시서 단위코드}`
- 커밋 메시지 규칙: `[{단위코드}] {한 일 요약}` — 예: `[A3] 핵심 기능 API 구현, AC-1~AC-4 통과`
- **머지 조건 (반드시 강제):**
  - AC 항목 전부 pass
  - 사람의 diff 리뷰 완료 (승인 없이는 머지 불가 — GitHub/GitLab의 "리뷰 필수" 브랜치 보호 규칙 사용)
  - CI(아래 2번) 통과
- 머지 후 즉시 A0 인수인계 문서 갱신 → 같은 커밋 또는 바로 다음 커밋에 포함

## 2. CI(자동 검증) 최소 구성

**원칙:** AC를 사람이 눈으로만 확인하지 않는다. 코드로 옮길 수 있는 AC는 전부 자동 테스트로 만든다.

TRD §6 테스트 시나리오 → 실제 테스트 코드로 변환하는 게 원칙입니다. 예시(GitHub Actions, 스택은 프로젝트에 맞게 교체):

```yaml
# .github/workflows/ci.yml (예시 — 실제 스택 확정 후 구체화)
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 의존성 설치
        run: echo "프로젝트 스택 확정 후 채우기"
      - name: 테스트 실행 (AC 기반)
        run: echo "TRD §6 기반 테스트 스위트 실행"
      - name: 결과를 PR에 코멘트로 남기기
        run: echo "pass/fail 요약을 사람이 리뷰 전에 볼 수 있게"
```

- **왜 PR 단계에서 도는가:** 머지되기 전에, 사람이 리뷰하기 전에 실패를 먼저 걸러내기 위함.
- 테스트가 불가능한 AC(예: UX 판단성 항목)는 CI 대신 사람 체크리스트로 남기되, TRD §6에 "자동화 불가 — 수동 확인"이라고 명시.
- **실제로 이 저장소의 `.github/workflows/ci.yml`에는 위 예시 하나 외에도 이미
  구성된 잡이 있다**: `repo-health`(저장소 상태 검증), `secret-scan`(gitleaks),
  `dependency-scan`(의존성 취약점 스캔 — `harness_13 §7` 참조), `lint`(정적분석/
  포맷팅/타입체크 — `harness_13 §4` 참조). 프로젝트 스택이 정해지면 `test`·
  `dependency-scan`·`lint` 세 잡의 내용만 채우면 된다.

## 3. 에이전트 실행 환경 / 권한 정책

**원칙:** AI가 실수로라도 스코프 밖에 영향을 못 미치게, 문서가 아니라 환경 자체를 제한한다.

- **파일시스템 범위:** 에이전트는 해당 단위의 작업 디렉토리 밖(다른 단위 코드, 설정파일 등)에 쓰기 권한을 주지 않는다. 필요하면 읽기 전용으로만 허용.
- **네트워크/외부 접근:** 프로덕션 DB, 실제 운영 API 키, 실제 사용자 개인정보는 에이전트 환경에 절대 넣지 않는다. 개발/샘플 DB만 연결.
- **민감정보 마스킹:** 개인정보 등 민감데이터는 실제 값 대신 샘플/마스킹 데이터를 사용한 시드(seed) 데이터셋을 별도로 준비해서 제공.
- **위험 명령 차단:** DB 스키마 DROP, 대량 삭제, 배포 명령 등은 에이전트가 직접 실행하지 못하게 하고, 사람이 승인 후 별도로 실행.

## 4. 에스컬레이션 프로토콜

**원칙:** "정책 불명확하면 멈추고 보고하라"는 규칙이 실제로 작동하려면, 멈춘 다음에 무슨 일이 일어나는지가 정의돼 있어야 한다.

| 상황 | 에이전트가 할 일 | 사람이 할 일 |
|---|---|---|
| TRD §7/작업지시서 §3의 "별도 확인 필요" 항목에 실제로 부딪힘 | 해당 지점에서 진행 중단, 무엇이 불명확한지 구체적으로 기록 | 그 항목에 대해 결정 → 작업지시서 §3 갱신 → 세션 재개 |
| TRD와 실제(코드/데이터)가 다름을 발견 | 임의로 어느 쪽을 따를지 정하지 말고 양쪽을 보고 | 어느 쪽이 맞는지 판단 → TRD 자체를 수정할지 결정 |
| AC를 도저히 충족 못 시키는 기술적 제약 발견 | 왜 불가능한지 근거와 함께 보고 | AC 자체를 재협상하거나 다른 접근법 지시 |

- **응답 기한 원칙:** 사람이 응답하기 전까지 해당 브랜치는 진행하지 않는다 (막힌 채로 다음 것을 임의로 진행시키지 않음).

## 5. 관찰 가능성(Observability) — 로그 보관

**원칙:** A0 문서는 사람이 요약한 결과다. 나중에 "왜 이렇게 됐지"를 재구성하려면 원본이 필요하다.

- 각 실행 단위 세션의 원본 로그(에이전트가 실행한 명령, 응답)를 `logs/{단위코드}_{날짜}.log`로 보관
- 최소한 다음은 반드시 남긴다: 최종 프롬프트 전문, 실패했던 시도와 재시도 이유, 최종 diff
- 로그는 커밋하지 않고 별도 저장(용량 문제) — 단, A0 문서에는 로그 파일 경로를 링크
- 사용한 AI 에이전트/모델명과 버전을 로그에 함께 기록한다 (`harness_04` 모델
  버전 변경 점검과 연동).
