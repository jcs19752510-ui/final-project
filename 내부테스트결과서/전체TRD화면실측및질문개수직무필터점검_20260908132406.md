## §1. 사용자 문의 2건에 대한 결론 (추측 아님, 코드+DB 실측)

### Q1. "질문이 계속 14개 나옵니다 — 맞는건가요?"
**아니오, 14는 설계된 고정값이 아닙니다.**
- `interview_service.py`의 `ended = result.action == "end_interview"` —
  면접 종료는 매 턴 **LLM이 스스로 판단**해서 정함. `llm.py` 시스템
  프롬프트, `config.py`, 전체 TRD 어디에도 "몇 턴에서 끝내라"는 목표/상한
  값이 없음(유일한 관련 조건은 마스터 TRD AC-M1 "**최소** 3턴 이상").
- 실제 DB 조회 결과, 같은 날 세션별 AI 턴 수가 **1건, 2건, 15건**(질문
  14개+마무리인사 1개)으로 전부 달랐음 — "14"는 사용자가 반복해서 보고
  계신 특정 리포트(`f43a8786-...`, 09-08 03:14 세션) 하나의 결과일 뿐,
  모든 세션이 14로 수렴하는 것이 아님.
- 그 세션은 답변이 전부 무음/잡음(STT가 ",,,,,,"로 인식)이었고, **오늘
  12시경 고친 "동일 질문 반복" 버그가 고쳐지기 전(오전 3시) 세션**이라
  6~13턴이 사실상 같은 질문의 반복이었음 — "14"라는 숫자 자체가 이미
  고쳐진 버그의 흔적이 섞인 결과라 앞으로는 재현되지 않을 가능성이 큼.
- §2-2에서 수정 이후 코드로 재현 실험 결과도 함께 기록함.

### Q2. "질문 시 백엔드만 나옵니다 — 맞는건가요?"
**절반만 맞습니다 — "카테고리 필터"는 없고, "LLM이 직무 맥락을 따라간다"가
정확한 설명입니다.**
- `question_service.py`의 `retrieve_candidates(db, limit=3,
  exclude_contents=already_asked)` 호출에는 `category` 인자가 전달되지
  않음 → 매 턴 LLM에게 주는 "참고 질문 후보"는 backend/frontend/
  algorithm/behavioral/general **전체 질문은행에서 무작위**로 뽑힘(필터
  없음, 마스터 TRD F-001 비고에도 이미 기록돼 있던 기존 한계).
- 다만 지원자 홈 화면(`CandidateHomePage.tsx`)의 "지원 직무" 입력란
  기본값이 `"백엔드 개발자"`로 미리 채워져 있고(수정 가능한 일반
  텍스트칸), 이 값이 매 턴 LLM 프롬프트에 "직무: OOO"로 그대로 들어가기
  때문에 **LLM이 스스로 그 직무 주제에 맞는 질문을 새로 생성**하는 것 —
  카테고리 필터링이 아니라 프롬프트 컨텍스트 효과.
- **직접 실측**: 같은 계정으로 지원 직무를 "프론트엔드 개발자"로 바꿔
  면접을 새로 시작해보니, 오프닝 질문 이후 바로 "UI/UX 구현 사례...
  프레임워크·라이브러리·CSS 솔루션..." 등 **명확히 프론트엔드 주제로
  전환**됨을 확인(§2-1). 즉 지원 직무 칸에 원하는 직무를 입력하면 그
  직무에 맞는 질문이 나온다 — 현재 "백엔드만 나온다"는 인상은 기본값을
  바꾸지 않고 쓴 결과로 보임.

## §4. 화면 테스트 중 새로 발견한 실제 버그 — `created_at` 고정 리터럴 버그 (발견·수정 완료)

### 발견 경위
AC-F8 확인 중 "원본 답변 오디오 관리" 목록 화면에서 **방금 막 제출한
오디오**의 표시 시각이 `"턴 1 · audio · 2026. 9. 7. 오후 9:30:31"`로 찍힌
것을 발견 — 실제 제출 시각(2026-09-08 낮)과 전혀 다름. 브라우저 시계
문제인지부터 배제(`new Date()`로 브라우저 시각이 실제로 정확함을 확인)
하고 DB를 직접 조회.

### 원인 (추측 아님, 실제 DB 스키마 조회로 확인)
```sql
SELECT pg_get_expr(d.adbin, d.adrelid) FROM pg_attrdef d ...
-- 결과: '2026-09-07 12:30:31.422073+00'::timestamp with time zone
```
`users`/`media_assets`/`coding_submissions`/`evaluation_reports`/
`whiteboard_snapshots` 5개 테이블의 `created_at` 컬럼 DEFAULT가 **함수
호출 `now()`가 아니라, 최초 `alembic upgrade head`를 실행한 그 순간의
값으로 굳어버린 고정 리터럴**이었음. 원인은 SQLAlchemy 모델/마이그레이션
코드에서 `server_default="now()"`처럼 **순수 Python 문자열**을 준
것 — `text("now()")`로 명시하지 않으면 DDL에 함수 호출이 아니라 그
시점의 리터럴 값으로 기록되는 것을 실제로 확인함(`transcripts` 테이블은
이미 예전에 다른 이유로 Python 쪽 콜러블 기본값을 쓰도록 고쳐져 있어서
이 문제가 없었음 — 나머지 5개 테이블에 같은 원인이 남아있던 것을 이번에
추가로 발견).

**증거**: 이 세션에서 방금 새로 가입한 `trdtest20260908@example.com`
계정조차 `created_at = 2026-09-07 12:30:31.422073+00`로 찍혀 있었음 —
즉 **이 DB에 있는 사실상 모든 사용자/미디어/코딩제출/리포트 행의
생성시각이 전부 같은 고정값**이었다는 뜻.

### 영향 범위
- **기능적 영향**: 없음(실제 로직에서 이 컬럼들로 정렬/판단하는 코드가
  없음을 `order_by(...created_at...)` 전수 검색으로 확인 — 유일하게
  정렬에 쓰이는 `Transcript.created_at`은 애초에 이 버그가 없었음).
- **표시/신뢰성 영향**: 있음. "원본 답변 오디오 관리" 목록, 향후 관리자
  화면 등에서 사용자에게 **잘못된 생성 시각**을 보여주고 있었음 — 생체
  데이터(N-003) 보관 이력의 정확성 문제로 이어질 수 있어 사소하지 않음.

### 수정
1. `app/models/user.py`, `media_asset.py`, `coding_submission.py`,
   `evaluation_report.py`, `whiteboard_snapshot.py` — `server_default=
   "now()"` → `server_default=text("now()")`로 수정(신규 fresh DB 구축 시
   재발 방지).
2. 신규 마이그레이션 `f6341f660dd1_fix_created_at_server_default_frozen_.py`
   추가 — 이미 있는 라이브 DB의 5개 테이블 컬럼 DEFAULT 절만
   `ALTER COLUMN ... SET DEFAULT now()`로 교정(**기존에 저장된 행의 값은
   건드리지 않음** — 과거 데이터를 임의로 재작성하는 것은 되돌리기 어려운
   결정이라 하지 않음, 필요하면 별도로 사람이 판단).
3. 최초 마이그레이션(`68f6341f989a`) 소스도 `sa.text('now()')`로 함께
   정정(향후 완전히 새 DB로 처음부터 구축할 경우를 대비한 예방 조치).

### 검증
| 항목 | 방법 | 결과 |
|---|---|---|
| 마이그레이션 적용 | `alembic upgrade head`(68f6341f989a → f6341f660dd1) | **PASS** |
| DDL 실제 반영 확인 | `pg_get_expr`로 `media_assets.created_at` 기본값 재조회 | **PASS** — `now()`로 변경 확인 |
| 신규 가입 시각 정확성 | `createdatfixtest@example.com` 신규 가입 → DB 조회 | **PASS** — `created_at`(04:20:00.117629)이 `db_now`(04:20:00.734128)과 0.6초 이내 일치 |

## §5. 종합 결론
1. 사용자 문의 2건 모두 "버그로 인한 이상 동작"이 아니라 **설계상 정상
   동작(직무 텍스트 기반 LLM 자율 판단)** 임을 코드+실측으로 확인. 다만
   지원 직무를 원하는 값으로 직접 입력해야 그에 맞는 질문이 나온다는 점은
   화면에 안내 문구가 없어 오해 소지가 있음 — 필요시 "지원 직무를 입력하면
   그 직무에 맞춰 질문이 생성됩니다" 같은 힌트 문구 추가를 고려할 수 있음
   (지금은 제안일 뿐, 사용자 결정 필요 — UI 변경 범위 확대라 자동으로
   진행하지 않음).
2. 프론트엔드 TRD AC-F1~F11 **11개 전부 PASS**(AC-F6은 기존과 동일하게
   도구 한계로 계약 수준 검증).
3. 화면을 실제로 띄우고 캡처하며 점검하는 과정에서 **아무도 모르고
