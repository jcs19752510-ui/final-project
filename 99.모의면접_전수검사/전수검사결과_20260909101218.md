| AI Worker Layer | LLM Orchestrator, Emotion Engine, STT Service | `app/ai/llm.py`, `app/ai/emotion.py`, `app/ai/stt.py` | 부분일치 | 컴포넌트는 존재하나 **별도 워커 프로세스가 아니라 Core API와 같은 프로세스 내 `BackgroundTasks`**로 실행(레이어 분리 없음) |

## H. 문서 간 불일치 (상세 텍스트 기획서 vs 요약 슬라이드)

**방법론**: 슬라이드 PDF 15페이지 전부(이전 검사는 4페이지만 샘플링했음 —
이번에 전수 재확인)를 PyMuPDF로 PNG 렌더링해 육안 확인하고, 본문 14페이지
전문(§1~§10)과 항목별로 대조함. 아래 원칙으로 분류: **(a) 슬라이드가
본문 내용을 시각적으로 요약만 한 경우(정보 손실은 있어도 모순 없음) →
불일치 아님**, **(b) 슬라이드와 본문이 실제로 다른 값/구조를 명시한 경우
→ "문서 간 불일치"로 별도 표기(아래 표), "미구현" 판정에는 포함하지 않음**.

15페이지 중 13페이지(표지, 문제/목표 요약, 기능 요약, 5-Layer 아키텍처,
기술스택 선정, 지연 파이프라인, RAG/프롬프트, 멀티모달 감정분석, 음성
처리, 루브릭, 로드맵, 보안/확장성, 결론, 산출물 체크리스트)는 전부 본문
내용을 그대로 시각화한 것으로 확인 — 모순 없음. **2페이지에서 실제
불일치를 발견함**:

| # | 위치 | 본문(1차 기준) | 슬라이드(참고) | 판정 |
|---|---|---|---|---|
| H-1 | API 응답 스키마 — `rubric_match` 필드 타입 | 본문 10~11페이지 "AI 평가 결과 저장(Save Evaluation)" JSON Schema: `"rubric_match": {"type": "object", "description": "사전 정의된 루브릭 항목별 달성 여부"}` — **object 타입** | 슬라이드 10번("데이터 무결성을 위한 스키마 및 API 설계") "Core API Interface Contract": `"rubric_match": "boolean"` — **boolean 타입** | **문서 간 불일치**(내용이 실제로 다름 — 슬라이드가 본문의 두 개 별도 스키마(Start Session 응답 + Save Evaluation 스키마)를 하나로 합치면서 `rubric_match`의 타입도 object→boolean으로 바뀌었고, 본문에 있던 `communication_clarity` 필드는 슬라이드에서 누락됨). **실제 구현과의 관계**: A REQ-F-007(§A)에서 이미 확인했듯 실제 코드(`app/ai/report.py` `ReportResult.pass_recommendation: bool`)는 `rubric_match`라는 이름의 필드 자체가 없고 `pass_recommendation`(boolean)이 유사한 역할을 대신함 — 그래서 이 불일치가 REQ-F-007의 "완전구현" 판정 자체를 바꾸지는 않으나, 두 원본 문서가 서로 다른 스펙을 제시하고 있었다는 사실은 별도로 기록함 |
| H-2 | C-1 5-Layer 아키텍처의 "레이어 개수" | 본문 5~6페이지 ERD 표는 `Presentation`/`Gateway`/`Application`/`Real-time`/`AI Services`/`Data` — **6개 레이어**로 서술(Application의 Core API·Signaling Server와 Real-time의 Media Server가 별도 행) | 슬라이드 4번은 제목 자체가 "5-Layer 아키텍처"이고, `Application`과 `Real-time`을 `Application & Real-time Layer` 하나로 합침 — **5개 레이어** | **경미한 문서 간 표현 차이**(포함된 실제 구성요소·기술스택 데이터는 본문·슬라이드가 100% 동일 — Core API/Signaling Server/Media Server가 다 들어있음. 다만 "몇 개 레이어로 부를지"라는 그룹핑/명명 자체가 다름). 위 §C-1 표는 슬라이드 쪽(5-Layer, "AI Worker Layer" 명칭)을 그대로 따랐다는 점을 명시 — 본문 기준으로는 "6-Layer"라고 부르는 것이 더 정확함 |

**"문서 간 신규 요구사항 없음"이라는 최초 검사 결론은 15/15 전수 확인
후에도 대체로 유지되나(위 13페이지), 정확히는 "완전히 없음"이 아니라
"위 2건을 제외하면 없음"으로 정정함.**

## 전체 요약

- **총 매트릭스 행 수**: A(7)+B(4)+C(9)+C-1(5)+D(5)+E(2)+F(12)+G(7)+부록(10) = **61행**(전부 근거 첨부해 판정 완료, 빈 칸 없음) **+ H(문서 간 불일치, 2건, 61행 카운트와는 별도 집계)**.
- **문서 간 불일치(§H)**: 슬라이드 15/15페이지 전수 재확인 결과 2건 — API 응답 스키마 `rubric_match` 타입(object vs boolean, H-1) 및 아키텍처 레이어 개수 표현(6-Layer vs 5-Layer, H-2, 경미). 둘 다 "미구현"이 아니라 별도 "문서 간 불일치"로 분류(지시서 규칙 반영) — A/C-1의 기존 판정은 변경 없음.
- **완전구현**: 2건(REQ-F-007, F-3/F-6/F-7/F-8/F-9는 F절 자체 항목이라 카운트 별도) — A~E 매트릭스 기준으로는 REQ-F-007 1건만 순수 "완전구현".
- **부분구현**: 다수(A의 F-002/F-004/F-006/N-004, D 전 테이블, G 전 Phase 등) — 이 프로젝트의 지배적 패턴.
- **미구현**: REQ-F-005(화이트보드), REQ-N-002(수평확장), 부록 문서 4~7종.
- **설계와 다르게 구현됨(의도적, ADR 근거 있음)**: A의 F-001/F-003, B의 N-001/N-002, C 전체, C-1 전체, E 전체 — 대부분 ADR 문서로 뒷받침됨.
- **설계와 다르게 구현됨(근거 문서 없음/확인 불가)**: D Interviews의 `overall_score` 죽은 컬럼(B REQ-N-003의 AES-256 항목은 2026-09-09 조치로 해소됨 — 아래 참조).
- **F 보안(2026-09-09 갱신)**: 원래 상 0건/중 4건(F-1/F-4/F-10/F-11)/하 2건/확인불가 2건이었으나, **F-1/F-4/F-10 3건이 조치 완료되어 운영 배포까지 재검증됨**. 남은 중간 심각도는 **F-11(샌드박스 파일시스템 격리) 1건**뿐이며, 이건 인프라 제약(Render 등 공유 PaaS 컨테이너에서 chroot/네임스페이스 권한 자체가 없음)으로 코드 수정만으로는 해결 안 되는 항목 — 별도 스코프 결정 필요.

이 문서는 최초 작성 시 코드 수정 없이 검사만 수행했으나, **이후 세션에서 F-1/F-4/F-10 3건을 실제로 조치·배포·재검증**했고 이 문서에도 그 결과를 반영했다(각 항목 셀 및 위 요약 참조, 내부테스트결과서 2건 근거). 남은 미해결 보안 항목은 F-11 하나이며, 이는 "고칠지 말지" 판단이 아니라 "현재 아키텍처로는 완전한 해결이 어려우니 스코프를 어떻게 가져갈지"의 결정 사항이다.
