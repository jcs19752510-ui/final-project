## 자동으로 결정한 것
1. **프론트엔드 착수를 진행한다** — 근거: 마스터 TRD §1의 화면 목록,
   release_plan.md의 "프론트엔드 착수 여부는 사람 결정 필요" 문구는
   "할지 말지"가 아니라 "언제 할지"의 타이밍 문제였고, 사용자가 이번
   세션에서 자동진행을 명시적으로 승인했으므로 지금 착수해도 스코프
   위반이 아니라고 판단.
2. **화면별 TRD를 쪼개지 않고 `docs/trd/aimock_frontend_trd.md` 하나로
   통합** — 근거: 라우팅/인증 컨텍스트/공통 API 클라이언트가 5개 화면
   전체에서 공유되는 하나의 응집된 엔지니어링 단위이고, 화면마다 TRD를
   쪼개면 공통 인프라(§0~§1)가 5번 중복되어 오히려 하네스 원칙(문서는
   상위 계약을 명확히 하기 위함)에 역행한다고 판단. 파일명은 `master`/
   `a0`처럼 "단위 코드 없는 전체 문서" 패턴을 프론트엔드에도 적용
   (`docs/tech_conventions.md` 파일명 규칙의 자연스러운 확장 해석).
3. **U2-c(화이트보드)/U3-b(표정·음성 타임라인)는 화면에 "준비 중"
   플레이스홀더만 두고 실제 구현은 하지 않는다** — release_plan.md의
   기존 Could/보류 분류를 그대로 계승, 새로 재논의하지 않음.
4. **작업 순서**: U1(인증) 화면부터 시작 — 다른 모든 화면이 로그인을
   전제로 하므로 가장 먼저 완성해야 나머지 화면을 실제로 테스트할 수
   있음(하네스 원칙 3 "선행 확인"과 동일한 논리를 프론트에도 적용).
