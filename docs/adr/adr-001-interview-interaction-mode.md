# ADR-001: 인터뷰 상호작용 모드 — 턴 기반 vs 실시간 스트리밍

- 날짜: 2026-09-07
- 상태: 승인됨
- 결정권자: 사용자 (AskUserQuestion으로 명시적 확인)

## 배경 (Context)

원본 기획서(`00 파이널 프로젝트 계획서/*.pdf`)의 REQ-N-001은 음성 인식→LLM
추론→음성합성까지 총 지연시간(End-to-End Latency) 800ms~1.5s 이내를
요구합니다. 이를 달성하기 위해 원본 설계는 다음을 전제합니다.

- Deepgram Nova-2 스트리밍 STT (유료, <300ms)
- WebRTC 기반 SFU/서버 사이드 미디어 처리 (Python aiortc 또는 GStreamer로
  클라이언트 스트림을 서버에서 수신·분기)
- VAD(Voice Activity Detection) + Turn-taking 알고리즘으로 실시간 개입
- Hume AI/ElevenLabs 스트리밍 TTS

실제 개발 조건(2026-09-07 확인)은 **개발자 1인, 기간 4주 이내, 예산은
Claude Code 구독료를 제외하면 전부 무료(오픈소스/무료 티어)만 사용**입니다.
이 조건에서 위 스택을 그대로 구현하는 것은 사실상 불가능합니다:
1) Deepgram·Hume AI·ElevenLabs는 모두 유료 API이고, 2) aiortc 기반 커스텀
SFU/미디어 서버는 그 자체로 수 주가 걸리는 별도 프로젝트급 난이도이며,
3) VAD+Turn-taking 실시간 개입 로직은 1인이 4주 안에 안정화하기 어렵습니다.

## 검토한 대안 (Options)

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 턴 기반(녹음 버튼/VAD로 발화 구간만 감지) | 구현 단순, 무료 스택(로컬 Whisper)으로 완결 가능, 4주 내 완성 가능성 높음 | "실시간 대화" 느낌이 약함, REQ-N-001(1.5s) 원안은 포기 |
| B. 브라우저 내장 Web Speech API로 준실시간 | 서버 STT 인프라 불필요, 중간결과 스트리밍 가능 | Chrome 의존, 인식 품질이 Google 서버에 종속, 오프라인 데모 불가 |
| C. 서버 사이드 스트리밍 직접 구현(WebSocket + 로컬 Whisper 스트리밍) | 원안과 가장 유사한 UX | 구현 난이도 최고, 1인/4주 내 완성 리스크 가장 큼 |

## 결정 (Decision)

**A안(턴 기반)을 채택한다.** 지원자가 "답변 시작" 버튼(또는 침묵 감지
VAD)으로 한 턴의 발화 구간을 명시적으로 구분하고, 해당 오디오를 로컬
faster-whisper로 일괄 변환 → LLM에 전달 → 응답 생성 → (선택) TTS 재생하는
**턴 기반 파이프라인**으로 REQ-N-001을 대체한다. 실시간 스트리밍 대화 UX는
이번 MVP 범위에서 명시적으로 제외(Won't)한다.

## 결과/트레이드오프 (Consequences)

- 포기하는 것: "실제 면접처럼 끊김없이 대화가 흐르는" 느낌, 실시간 개입
  (REQ-F-003)은 "턴이 너무 길면 다음 질문으로 넘어가기 전에 안내 문구를
  보여준다" 수준으로 축소.
- 나중에 발목 잡을 수 있는 지점: 만약 향후 실제 서비스로 발전시키려면
  프론트엔드 상호작용 모델(턴 기반 상태 머신)을 스트리밍 모델로 다시
  설계해야 함 — 이번 결정은 "MVP 한정" 임을 마스터 TRD에 명시.
- 이 결정은 SRS의 REQ-N-001을 대체하므로, 마스터 TRD §비기능요구사항에도
  동일하게 반영한다.
