# 마스터 TRD §2/§3/§5 라인 단위 검토 (2026-09-08)

> `docs/trd/aimock_master_trd.md` §2(기능요구사항)/§3(비기능요구사항)은
> 문서 상단에 "[AI 초안 → **사람 확인 필요**]"로 명시된 채 지금까지 사람이
> 라인 단위로 검토한 적이 없었습니다(A0 §4). 사용자가 "20년차 기준으로
> 재검토"를 요청해, 각 줄을 실제 코드(`src/backend/`, `src/frontend/`)와
> 대조한 결과를 정리합니다. **이 문서는 검토 결과 초안이며, 각 줄의 최종
> 승인/반려는 사람이 합니다** — 하네스 원칙 2(에스컬레이션)에 따라 스펙
> 문구를 AI가 임의로 확정하지 않습니다.

## 이번 검토 중 실제로 고친 것 (승인 대기 아님 — 이미 완료·재검증됨)

실행하다 발견한 **이미 승인된 정책(ADR-004)이 실제로는 실행되지 않고
있던 버그**는 그 자리에서 고쳤습니다(새 정책 결정이 아니라 기존 승인
사항을 실제로 동작하게 만든 것이므로 하네스 원칙 8 대상 아님):

- **원본 오디오 미보관 버그**: `interview_service.submit_turn()`이 STT
  변환에만 오디오를 쓰고, U1-b가 이미 갖추고 있던 암호화 저장
  (`media_service.upload_media`)을 호출하지 않아서, ADR-004("원본
  오디오는 지원자 삭제 요청 전까지 암호화 보관")가 실제 면접 흐름에서는
  전혀 지켜지지 않고 있었습니다. → 턴 제출 시 자동으로 암호화 저장하도록
  연결(`src/backend/app/services/interview_service.py`).
- **AC-M6(원본 미디어 삭제) 프론트엔드 UI 부재**: 삭제 API(U1-b)는
  있었지만 "리포트 화면에서" 요청할 수 있는 화면이 아예 없었습니다(제가
  이전 세션에서 텍스트 안내만 넣고 실제 구현을 빠뜨렸습니다). →
  `GET /api/v1/interviews/{id}/media`(신규) + `ReportPage.tsx`의
  "원본 답변 오디오 관리" 섹션으로 조회·삭제 가능하게 구현, 실제
  브라우저+백엔드로 검증 완료(내부테스트결과서 참조).
- 회귀 테스트 4건 추가(백엔드 `test_ac2b`/`test_ac2c`, 프론트 `ReportPage.test.tsx`
  "AC-M6" 테스트 등).

## §2. 기능 요구사항 — 라인별 검토

| ID | TRD 문구 | 실제 코드 대조 결과 | 판정 |
|---|---|---|---|
| F-001 | "적응형 꼬리질문: ... RAG로 질문은행(pgvector)에서 다음 질문 후보 검색" | `question_service.retrieve_candidates()`는 카테고리/난이도 필터도 없이 **전체 질문을 무작위 셔플해 3개 반환**(`app/services/question_service.py:24-33`, `interview_service.py:102`에서 인자 없이 호출). pgvector 컬럼은 스키마에 있지만 실제 유사도 검색에 쓰이지 않음. **적응성 자체는 LLM이 대화 history 전체를 프롬프트로 받아 스스로 판단하는 방식으로 별도로 존재**(이 부분은 진짜 동작함, Gemini 키 확보 후 검증 필요) | ⚠️ **문구가 실제보다 과장됨** — "RAG/후보 검색" 부분은 사실과 다름. "LLM이 전체 대화 맥락을 보고 다음 질문을 생성"으로 정정 권고 |
| F-002 | "멀티모달 입력: 텍스트(코드)+오디오(답변)+이미지(화이트보드/표정 프레임)" | 텍스트(코드)·오디오는 구현·검증됨. **이미지 입력(화이트보드/표정 프레임)은 U2-c/U3-b가 미착수라 전혀 없음** | ⚠️ Must로 분류돼 있으나 실제로는 부분 구현. release_plan.md에는 U2-c/U3-b 상태가 이미 정확히 기록돼 있음 — **§2 표만 갱신 필요**(중복 기록 아님, 최신화 누락) |
| F-003 | "답변 시간 초과 시 안내 문구로 다음 질문 유도" | 실제 구현은 **시간(wall-clock)이 아니라 답변 텍스트 길이**(`settings.turn_max_answer_chars`)로 판단(`interview_service.py:90`). "시간 초과"가 아니라 "답변이 너무 길면" 조건 | ⚠️ 문구와 실제 트리거 조건이 다름 — 턴 기반 구조상 실시간 타이머 계측이 어려워서 나온 합리적 대체지만, 문서에 그 사실이 반영 안 됨 |
| F-004 | "라이브 코딩: ... AI가 정답여부/시간복잡도/스타일 평가" | 코드 실행(U2-b)은 완료. "AI 평가"는 U4로 이관돼 리포트 생성 시 코드 제출 이력을 LLM 컨텍스트에 포함하지만, **정답여부/시간복잡도/스타일을 구조화된 필드로 분리 평가하지는 않음** — `ReportResult`엔 그런 필드가 없고 `summary_text`/`star_analysis`에 뭉뚱그려 들어감(Gemini 키 없어 실제 출력 미검증) | ⚠️ 이관 결정 자체는 이미 자동진행 로그로 기록됨(U2b workorder). §2 문구에 "구조화된 평가 필드 없음"을 반영할지는 사람 판단 필요 |
| F-005 | 화이트보드 — Could | 미착수, release_plan과 일치 | ✅ 일치(의도된 미착수) |
| F-006 | "STAR 구조 분석, 핵심 키워드, 발화속도, 표정 타임라인" | STAR·키워드는 구현됨. **"발화속도" 계산 로직이 코드 어디에도 없음**(키워드 추출만 있음, `keyword_extractor.py`). 표정 타임라인은 U3-b 미착수라 항상 빈 배열 | ⚠️ "발화속도"는 이번 검토에서 새로 발견 — 구현된 적이 없는 항목이 Must 요구사항 표에 그대로 남아있음 |
| F-007 | 루브릭 1~5점 + 합격/불합격 추천 | `ReportResult`에 technical/communication/cultural_fit(1~5) + `pass_recommendation` 있음, 구현·검증 완료(Fake 기준) | ✅ 일치 |

## 사람이 결정할 것 (요약)

1. F-001/F-003/F-006 문구를 실제 구현에 맞게 고칠지, 아니면 실제 구현
   쪽을 문구에 맞게 확장(예: 진짜 벡터 검색 도입, 발화속도 계산 추가)할지.
   **4주/1인 규모 감안하면 "문서를 실제에 맞게 정정"을 권고**하지만
   최종 판단은 사람 몫입니다.
2. N-004의 `key_observations` 필드명 — 스키마를 바꿀지 문서를 정정할지.
3. F-002(이미지 입력)/F-004(구조화된 코드 평가)를 Must에서 Should로
   재분류할지 — 이미 사실상 그렇게 운영되고 있음(release_plan.md의
   U2-c/U3-b 분류와는 별개로, §2 표 자체가 이를 반영 안 함).
