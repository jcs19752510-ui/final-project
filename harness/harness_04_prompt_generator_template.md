# 프롬프트 생성기 템플릿

> 목적: TRD + 작업지시서 + 이전 A0 문서, 이 3개를 조합해서
> AI 에이전트(Claude Code 등)에게 넘길 최종 프롬프트를 일관된 형식으로 만듭니다.
> 매번 즉흥적으로 프롬프트를 쓰면 세션마다 품질이 들쭉날쭉해집니다 — 이 템플릿으로 표준화하세요.

---

## 조합 규칙

최종 프롬프트는 항상 아래 6개 블록을 이 순서로 포함합니다.

### 블록 1 — 역할과 원칙 고정
```
당신은 이 프로젝트의 백엔드/프론트엔드 구현을 담당하는 개발 에이전트입니다.
다음 원칙을 반드시 지키세요:
1. 스펙에 없는 기능을 임의로 추가하지 마세요.
2. 정책이 불명확한 부분을 발견하면 임의로 판단하지 말고, 진행을 멈추고 보고하세요.
   (단, 아래 §미결항목에 기본값이 명시된 것은 그 기본값을 따라 진행하세요.)
3. 원본 코드/실제 데이터가 스펙과 다르면 실제 쪽을 우선하고, 이 사실을 반드시 보고하세요.
4. 작업이 끝나면 AC 각 항목에 대해 pass/fail을 스스로 점검한 결과를 보고하세요.
5. 왜 그렇게 구현했는지 판단 근거를 결과 보고에 포함하세요.
```

### 블록 2 — 이번 세션 범위 (작업지시서 §1, §2 발췌)
```
[이번에 할 것]
(작업지시서 §1 체크리스트 붙여넣기)

[하지 않을 것]
(작업지시서 §2 붙여넣기)
```

### 블록 3 — 스펙 (TRD §1~§4 발췌)
```
(TRD의 데이터구조, 함수명세, 워크플로우, 상태코드 붙여넣기)
```

### 블록 4 — 완료 기준 (TRD §5, §6 발췌)
```
(AC와 테스트 시나리오 붙여넣기 — 이것이 최종 검증 기준임을 명시)
```

### 블록 5 — 미결 항목 및 기본값 (작업지시서 §3 발췌)
```
(미결 항목 표 붙여넣기 — "별도 확인 필요" 항목은 특별히 강조)
```

### 블록 6 — 이전 세션 맥락 (A0 §3, §5 발췌, 있는 경우만)
```
[이전 세션에서 발견된 편차 — 참고하세요]
(A0 §3 붙여넣기)

[이번 세션 착수 전 확인해야 할 것]
(A0 §5 붙여넣기)
```

## 체크리스트 (프롬프트 발송 전 최종 확인)
- [ ] 블록 1의 원칙 문구가 누락 없이 포함됐는가?
- [ ] 범위(블록 2)가 작업지시서와 정확히 일치하는가? (요약하다가 빠뜨린 항목 없는지)
- [ ] AC(블록 4)가 모호한 표현 없이 측정 가능한가?
- [ ] 이전 세션의 편차(블록 6)가 있다면 빠짐없이 포함됐는가?
- [ ] 프롬프트만 읽고도, 이 대화 맥락을 전혀 모르는 사람(AI)이 작업을 시작할 수 있는가?

## 에이전트/모델 버전 변경 시 점검 [사람 작성 — 버전 변경 시점마다]
> 블록 1 "역할과 원칙"은 특정 모델 세대로 검증된 문구입니다. 사용하는
> 에이전트/모델이 바뀌면(예: 다음 세대 모델로 전환) 같은 프롬프트가 다르게
> 해석될 수 있습니다.

- [ ] 모델/에이전트 버전이 바뀌면, 최근 통과했던 단위 하나를 같은 프롬프트로
      재실행해 결과가 동일한 방향으로 나오는지 회귀 확인한다.
- [ ] 회귀 확인에서 차이가 발견되면 블록 1을 재검토하고, 필요시 `harness_06`
      실패 패턴 라이브러리에 등록한다.
- [ ] 사용한 모델/에이전트 이름·버전을 세션 로그(`harness_05 §5`)에 함께
      기록해, 나중에 "이 결과가 어느 모델 기준이었는지" 추적 가능하게 한다.
