# 하네스 시스템 개요 및 SOP

> 이 문서는 하네스 전체를 처음 접하는 사람(미래의 나 자신 포함)이 5분 안에
> "이게 뭐고, 왜 있고, 어떤 순서로 쓰는지"를 파악할 수 있도록 만든 진입 문서입니다.
> 그림으로 전체 지도부터 보고 싶다면 `harness_00_definition.md`를 먼저 보세요.

## 1. 하네스란 무엇인가

AI 에이전트(Claude Code 등)에게 개발 작업을 위임할 때, **자율성을 안전한 범위로 제한하면서도
반복 가능하게 만든 거버넌스 프레임워크**입니다.

핵심 전제: AI는 "계획 → 실행 → 관찰 → 조정" 루프를 스스로 잘 돌립니다(에이전시).
하지만 **목표 자체를 잘못 해석하거나, 스코프를 넘어서거나, 되돌리기 어려운 결정을
혼자 내리는 것**은 사람이 막아야 합니다(거버넌스). 하네스는 이 거버넌스를 문서 형태로
구조화한 것입니다.

## 2. 문서 5종과 역할

| 순서 | 문서 | 답하는 질문 | 작성 주체 |
|---|---|---|---|
| 1 | `01_trd_template.md` | 무엇을 만드는가 (목표/스펙) | 사람 (AI 초안 지원 가능) |
| 2 | `02_work_order_template.md` | 이번 세션은 어디까지 하는가 (경계) | 사람 |
| 3 | (내장) AC/테스트케이스 | 성공을 어떻게 증명하는가 | 사람 (TRD §5 안에 포함) |
| 4 | `04_prompt_generator_template.md` | AI에게 정확히 뭐라고 시키는가 | 사람+AI 조합 |
| 5 | `03_handoff_template.md` (A0) | 뭘 했고 뭐가 남았는가 | AI 초안 → 사람 검증 |

## 3. 표준 실행 절차 (SOP)

### Phase A — 프로젝트 착수 (1회만)
1. 요구사항 정의 (기능 + **비기능**: 동시성/권한/감사/개인정보) — 사람이 직접
2. 데이터 모델(ERD) 확정 — 되돌리기 가장 어려운 결정이므로 가장 먼저, 가장 신중하게
   (→ `harness_08_adr.md`에 결정 근거 기록)
3. 기술 스택/환경설정 문서 확정 (변경 시 전체 재검토 필요하므로 초반에 고정)
   (→ `harness_13_tech_conventions.md`로 전역 표준화, `harness_08_adr.md`에 근거 기록)
4. 마스터 TRD 작성 (전체 화면/기능 목록과 흐름)
5. 릴리스 우선순위 확정 (`harness_07_release_planning.md` — MoSCoW/MVP 범위)
6. 위험도 기준으로 실행 단위 순서 결정 (화면 순서 아님 — 되돌리기 어려운 것부터,
   `harness_07`의 가치 순위와 매트릭스로 조합해 최종 확정)

### Phase B — 단위별 실행 루프 (단위 수만큼 반복)
1. 해당 단위의 TRD 세부 스펙 작성 (`01_trd_template.md` 사용)
2. AC/테스트케이스 확정 (TRD §5 — **코드 작성 전에 반드시 먼저**)
3. 작업지시서 작성 (`02_work_order_template.md` 사용) — 범위, 하지 않을 것, 미결항목+기본값
4. 프롬프트 생성 (`04_prompt_generator_template.md` 사용) → Claude Code 등에 위임
5. AI 실행 (계획→코드→실행→디버깅→재시도, 이 안쪽은 AI의 자율 루프)
6. **사람 검증** — AC 기준으로 pass/fail 판정, diff 리뷰
7. 통과 시 버전관리 커밋 / 실패 시 4번으로 재위임 (스펙 자체가 틀렸다면 1번으로 회귀)
8. 인수인계 문서(A0) 갱신 (`03_handoff_template.md`) — 완료/미결/발견된 편차 기록

### Phase C — 통합 및 마감
1. 단위 간 연결 지점 E2E 테스트 (사람이 직접 손으로 확인)
2. 배포 실행 (`harness_09_deployment_runbook.md`) 및 운영 모니터링 체계 구성
   (`harness_17_monitoring.md`)
3. 최종 A0 문서를 프로젝트 회고로 정리 (다음 프로젝트 하네스 개선에 반영,
   `harness_06_meta_improvement.md`)

## 4. 무조건 지켜야 할 규칙 (타협 불가)

1. 되돌리기 어려운 결정(데이터 모델, 권한 구조, 삭제 정책)은 AI가 혼자 확정하지 못한다 — 후보만 제시, 최종 승인은 사람.
2. AC/테스트케이스는 코드 생성 **전에** 확정한다.
3. 한 실행 단위의 결과물은 다음 단위로 넘어가기 전에 반드시 리뷰한다.
4. 검증된 단위는 즉시 버전관리에 커밋한다 (언제든 롤백 가능해야 함).
5. AI의 판단 근거를 기록하게 한다 — 코드만 받지 않는다.
6. 개인정보/민감데이터는 실제 값 그대로 AI에게 주지 않는다 (마스킹/샘플 데이터 사용).
7. 스펙 문서는 단일 진실 공급원(single source of truth)을 유지한다 — 여러 버전이 떠돌지 않게.
8. AI 결과물은 "능력 있지만 검증 안 된 신입의 초안"으로 취급한다 — 신뢰가 아니라 검토가 기본값.

## 5. 파일명 규칙

- 영문/숫자만 사용 (한글·공백 섞인 파일명은 일부 환경에서 열림 문제 발생 이력 있음)
- 형식: `{프로젝트코드}_{단계코드}_{문서유형}.md`
  - 예: `{project}_a3_trd.md`, `{project}_a3_workorder.md`, `{project}_a0_handoff.md`
    (`{project}`는 프로젝트별 짧은 영문 코드로 착수 시 정함)
- 문서유형 약어: `trd`(스펙), `workorder`(작업지시서), `handoff`(인수인계), `prompt`(생성된 프롬프트)

## 6. 품질 게이트 체크리스트 (매 단위 완료 시 확인)

- [ ] AC 항목이 전부 pass인가?
- [ ] 비기능 요구사항(동시성/권한/감사/개인정보)이 이번 단위에 해당된다면 반영됐는가?
- [ ] AI가 스펙에 없는 것을 임의로 추가하거나 생략하지 않았는가? (diff 리뷰)
- [ ] 다음 단위가 이번 단위의 산출물(API, 테이블 등)에 의존한다면, 인터페이스가 문서화됐는가?
- [ ] A0 문서에 이번 세션 내용이 반영됐는가?

## 7. 실행 단위(unit) 크기 산정 기준
> TRD/작업지시서/A0/비용추적/병렬작업이 전부 "단위"를 기본 값으로 삼는데,
> 단위를 너무 크게 자르면 AC가 뭉뚱그려지고 리뷰가 부실해지며, 너무 잘게
> 자르면 문서 오버헤드가 실제 작업량을 넘어섭니다. Phase A-6(실행 단위 순서
> 확정)에서 마스터 TRD를 단위로 쪼갤 때 아래 기준을 적용하세요.

**적정 크기 (경험칙)**
- AI 세션 1~2회, 사람 리뷰 기준 반나절~3일 이내에 AC까지 통과 가능한 규모
- TRD §5 AC 개수가 대략 3~8개 사이 (10개를 넘으면 너무 크다는 신호)

**너무 크다는 신호**
- 여러 화면/여러 API 그룹이 하나의 TRD에 섞여 있다
- 작업지시서 §1 체크리스트 항목이 5개를 넘는다
- AC가 10개를 넘거나, AC 하나가 사실은 여러 개의 검증을 담고 있다

**너무 작다는 신호**
- 매 단위마다 드는 문서 작성(TRD/작업지시서/A0) 오버헤드가 실제 코드 작업량보다 크다
- `harness_15` 의존관계 다이어그램의 노드 수가 화면/기능 수보다 훨씬 많다

**쪼개는 기준**
- 데이터모델 경계, API 경계, 화면 경계 중 **하나**를 기준으로 자른다 — 여러
  경계를 동시에 가로지르는 단위(예: "로그인+데이터관리 화면 절반")는 지양한다.
- 쪼갠 뒤에는 `harness_15_parallel_work.md` §2로 의존관계를 다시 확인한다.
