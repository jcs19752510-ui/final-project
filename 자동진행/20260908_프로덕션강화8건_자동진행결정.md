## 자동으로 진행한 것과 판단 근거

1. **프론트엔드 유닛테스트 도입(Vitest)** — API 클라이언트 에러 파싱,
   AuthContext, ReportPage(409 회귀) 총 16개 테스트 작성. 새 테스트
   프레임워크 도입이지만 개발 도구일 뿐 런타임 아키텍처에 영향 없어
   자동진행 범위로 판단.
2. **CI에 프론트 빌드/테스트 단계 추가** — 순수 CI 배선, 위험 없음.
3. **프로덕션 정적 서빙(nginx) 추가** — `src/frontend/Dockerfile`,
   `nginx.conf`, `docker-compose.yml`에 `profiles: ["prod"]`로 추가해
   **기본 개발 흐름(`docker compose up -d`)에는 영향 없도록** 격리.
   기본값을 건드리지 않는 추가라 자동진행 범위로 판단.
4. **로그인 브루트포스 방어(레이트리밋)** — 인메모리 슬라이딩 윈도우
   (ADR-003 "Redis 없음"·ADR-005 "단일 인스턴스" 결정과 일치). 새 정책
   이지만 "권한 구조"나 "삭제 정책" 같은 되돌리기 어려운 결정이 아니라
   순수 방어 조치라 자동진행.
5. **JWT 만료 시 자동 로그아웃/재로그인 유도** — 프론트 UX 개선, 백엔드
   계약 변경 없음.
6. **ADR-007(샌드박스) 재검토** — **B안(Piston)/C안(Docker-in-Docker)로의
   전환은 하지 않음** — 이건 새 인프라 의존성을 들이는 아키텍처 전환이라
   하네스 원칙 8("되돌리기 어려운 결정 금지") 대상으로 판단, 사람 승인
   없이 진행하지 않음. 대신 A안 내에서 즉시 가능한 강화(`resource.setrlimit`
   CPU/메모리 상한)만 추가 — 이건 §7에 이미 "검토 여지"로 적혀있던
   항목을 채운 것뿐이라 자동진행.
7. **dompurify 취약점 패치** — `npm overrides`로 패치 버전 강제, 기존
   monaco-editor 동작에 영향 없음을 브라우저로 직접 재확인 후 적용. 새
   의존성 도입이 아니라 기존 의존성의 패치 버전 강제라 위험 낮음.
8. **마스터 TRD §2/§3 라인 검토** — 검토 자체는 수행했으나, **문서 내용
   확정은 사람 승인 사항이라 자동으로 문구를 고치지 않고**
   `docs/trd/aimock_master_trd_review_20260908.md`에 결과만 정리해
   사람이 빠르게 승인/반려할 수 있게 준비.
